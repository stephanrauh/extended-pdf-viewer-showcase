Start with the Minimal CSP tab: that policy is the smallest one the viewer runs under, measured directive by directive on an empty Angular application. Before it loads pdf.js, the viewer runs a small probe that decides whether this browser can run the modern bundle or needs the legacy one. The probe has to be a separate script, because it deliberately uses syntax an old browser cannot parse. [useInlineScripts] — which defaults to true — chooses how it is delivered: inline, saving one round-trip for op-chaining-support.js, but requiring 'unsafe-inline' in your script-src. Set it to false and the probe is loaded as a normal file, which any script-src 'self' allows. Toggle the checkbox and watch the network tab.

You do not have to get this right for the viewer to work: if the inline probe is blocked, the viewer notices the CSP violation and re-loads the same probe from the file. Setting [useInlineScripts]="false" is still worth it, because it avoids the blocked attempt — and with it the violation your browser console (and your CSP report endpoint) records.

pdf.js decodes JBIG2 / JPEG2000 images via small WebAssembly modules. A CSP that omits 'wasm-unsafe-eval' blocks them — in the worker as well as in the page. Nothing breaks: pdf.js downloads the .wasm, fails to compile it, and falls back to the *_nowasm_fallback.js sibling on its own. Output pixels match; only decode speed differs. Set pdfDefaultOptions.useWasm = false to skip the download that is going to fail anyway, or add 'wasm-unsafe-eval' to script-src to keep the faster path.
